## Q1：HashMap 在 JDK 8 中怎样完成 put、扩容与树化？

**短回答：**

结论：HashMap 先定位桶，再按空桶、同键、链表或红黑树分支写入；扩容通过容量翻倍重新分配桶，树化只在桶和表容量同时达到条件时发生。

**原理：**

哈希值会把 key 的高位扰动到低位，再以 `(n - 1) & hash` 定位桶。冲突后先比较哈希与 equals；链过长时，只有数组容量至少为 64 才树化，否则优先扩容。扩容到两倍后，旧桶节点只会留在原索引或移动到 `原索引 + oldCap`，因为新增的最高有效位决定去向。HashMap 不提供并发写安全，resize 与覆盖写都不能用“偶尔没出错”证明安全。

**代码 / 场景：**

订单属性缓存预估有十万条且读多写少时，应先合理设置 initialCapacity，减少扩容停顿；若被多线程共享，应改用 ConcurrentHashMap，而不是给 HashMap 的单次 put 结果做乐观假设。验证可构造碰撞 key，观察树化前后桶形态并压测扩容峰值。

**递进追问：**

1. **为什么容量通常取 2 的幂？**

   这样可以用位与替代取模，并使扩容后节点仅按新增的一位拆成两个桶，避免完整重算索引。

2. **树化后查询就一定是 O(log n) 吗？**

   只有冲突桶进入红黑树分支时才接近该复杂度；整体还受哈希质量、equals 成本和表容量影响。

**易错点：**

- 把树化阈值说成唯一条件，漏掉最小表容量限制。
- 把 HashMap 的常规操作复杂度当成并发安全保证。

## Q2：ConcurrentHashMap 在高并发更新时如何避免整表锁？

**短回答：**

结论：JDK 8 的 ConcurrentHashMap 以桶为并发粒度，空桶通过 CAS 安装首节点，冲突桶通过同步桶头完成修改，扩容时允许多个线程协助迁移。

**原理：**

读取大多不加互斥锁，依赖 volatile 可见性读取表和节点；写入空桶先 CAS，失败后重试，非空桶再对桶头同步并在锁内完成链表或树操作。扩容阶段使用转发节点标记已迁移桶，其他写线程可参与 transfer。计数不是每次都竞争同一个全局变量，而采用分散计数后汇总，降低热点竞争。它保证单次映射操作的线程安全，却不自动保证“先读再写”这一组合业务原子性。

**代码 / 场景：**

积分扣减若先 get 再 put，即使容器换成 ConcurrentHashMap 仍会丢更新；应使用 compute、merge 或把业务状态放入具有版本约束的存储。验证时用固定线程数并发累加，比较 get-put 与 compute 的最终总数，并记录扩容期间延迟。

**递进追问：**

1. **为什么 ConcurrentHashMap 不允许 null？**

   并发读取返回 null 时必须明确表示“没有映射”，否则无法区分真实 null 值与并发删除后的不存在。

2. **size() 能否作为并发控制条件？**

   不能。并发修改期间统计值适合监控和估算，不应拿来决定必须精确执行一次的业务分支。

**易错点：**

- 只背“CAS 加 synchronized”，却说不清空桶和冲突桶各走哪条路径。
- 误以为线程安全容器能让多步业务逻辑天然原子。

## Q3：遍历集合时怎样安全地新增或删除元素？

**短回答：**

结论：增强 for 或普通 Iterator 遍历期间不能直接调用集合自身的结构性修改；删除应使用迭代器方法，复杂增删可先收集变更或选用并发容器。

**原理：**

ArrayList 的迭代器记录创建时的 modCount 期望值，每次 next 或 remove 都会检查集合实际修改计数。集合绕过迭代器发生结构变化后，后续检查会尽力抛出 ConcurrentModificationException；这是快速失败诊断，不是线程安全机制，也不保证每次都抛。Iterator.remove 会同步更新期望计数，因此可在单线程遍历中安全删除当前元素。新增位置、跨线程修改和批量过滤应使用专门 API 或快照策略。

**代码 / 场景：**

清理过期会话时，单线程可以使用 `iterator.remove()`；若条件只是过滤，`removeIf` 更清楚。若读远多于写且需并发遍历，可评估 CopyOnWriteArrayList，但要压测写时数组复制和内存峰值，而不是看到“不会报错”就采用。

**递进追问：**

1. **fail-fast 是否能检测所有并发修改？**

   不能。它是尽力检测的错误提示机制，规范不承诺在所有竞态下必然抛出异常。

2. **CopyOnWriteArrayList 为什么适合读多写少？**

   迭代读取固定数组快照而无需锁，但每次结构写会复制数组，写多时吞吐和内存成本很高。

**易错点：**

- 把 ConcurrentModificationException 当作可靠的并发控制手段。
- 在大集合高频写场景盲目换成 CopyOnWriteArrayList。

## Q4：业务代码该怎样在 ArrayList、LinkedList 与队列之间选型？

**短回答：**

结论：默认随机访问和顺序追加优先 ArrayList；频繁从两端操作应考虑 ArrayDeque；LinkedList 只有持有节点位置时插删才有优势，不能只按“大量插入”选择。

**原理：**

ArrayList 使用连续引用数组，随机访问 O(1)，尾部追加摊销 O(1)，中间插删需要移动后续引用。LinkedList 查找第 i 个元素先走链，定位本身 O(n)，因此“中间插入 O(1)”只有已经拿到节点时才成立；每个节点还增加前后指针和对象开销。ArrayDeque 以循环数组提供两端 O(1) 操作，通常比 LinkedList 更适合作为栈或队列。选型还应考虑缓存局部性、内存占用和实际访问模式。

**代码 / 场景：**

批量组装响应 DTO 并按下标读取时使用预估容量的 ArrayList；任务调度需要从头取、从尾补时使用 ArrayDeque。用 JMH 或真实请求回放比较吞吐、分配率与 GC，而不是只列复杂度表。

**递进追问：**

1. **ArrayList 扩容是否会使每次 add 都是 O(n)？**

   不会，只有容量不足的少数操作需要复制，连续追加的平均成本仍是摊销 O(1)。

2. **LinkedList 能否实现高性能队列？**

   功能上可以，但节点分配和局部性较差；无特殊需求时 ArrayDeque 通常更合适。

**易错点：**

- 把“链表插入 O(1)”忽略定位节点的 O(n) 成本。
- 忽略对象分配、CPU 缓存和 GC，仅凭大 O 记号选型。

## Q5：StringBuilder 与 StringBuffer 的线程安全差异应如何落到场景？

**短回答：**

结论：两者都维护可变字符序列，StringBuffer 的公开方法带同步语义；线程封闭的字符串拼接优先 StringBuilder，共享可变实例才需要额外并发设计。

**原理：**

不可变 String 每次拼接可能产生中间对象，编译器可对简单表达式做优化，但循环和动态拼接常使用可变缓冲。StringBuffer 通过方法同步保护单次调用，代价是竞争与内存屏障；它并不保证跨多个调用的业务操作原子，例如先 length 再 append 仍可能被其他线程插入。StringBuilder 无同步成本，适合局部变量或明确线程封闭的构建过程。共享日志内容更适合每请求独立构建后一次提交。

**代码 / 场景：**

生成一条审计日志时，在请求线程内创建 StringBuilder，完成字段转义后一次写出；不要把一个全局 StringBuffer 当成日志队列。验证应包含多线程内容完整性测试，并观察锁竞争，而非只比较单线程耗时。

**递进追问：**

1. **使用 StringBuffer 后组合操作一定安全吗？**

   不一定。多个同步方法之间仍可被其他线程穿插，组合不变量需要外部锁或重构为单次操作。

2. **字符串常量相加为什么可能没有运行时开销？**

   编译期可确定的常量表达式会被折叠；运行时循环拼接仍需关注中间对象和容量扩展。

**易错点：**

- 把“方法 synchronized”误说成任意业务序列都具备原子性。
- 为了所谓安全把线程局部 StringBuilder 全部替换成 StringBuffer。

## Q6：双亲委派如何工作，什么时候才有理由打破它？

**短回答：**

结论：类加载器先把加载请求交给父级，父级无法完成时才由当前加载器查找；它保护核心类唯一性和基础安全，打破必须有明确隔离或扩展需求。

**原理：**

加载、链接、初始化是不同阶段；ClassLoader 的典型 loadClass 先检查已加载类，再委派父加载器，最后调用 findClass。类的身份由“全限定名加定义它的类加载器”共同决定，因此同名 class 被两个加载器定义也不是同一类型。插件容器、应用服务器隔离和 SPI 可能需要子优先或线程上下文类加载器，让父层框架看到子层实现，但必须控制依赖边界与卸载引用。

**代码 / 场景：**

支付插件按租户加载时可为每个插件建立受限类加载器，只开放稳定 SPI；升级后释放线程、ThreadLocal、驱动注册等强引用，再观察旧加载器是否可回收。若只是普通业务依赖，不应自定义加载顺序。

**递进追问：**

1. **两个同名类为什么可能无法强转？**

   因为定义它们的类加载器不同，JVM 认为它们拥有不同的运行时类型身份。

2. **SPI 为什么常使用线程上下文类加载器？**

   父加载器定义的框架接口需要发现由子加载器提供的实现，反向借用上下文加载器完成查找。

**易错点：**

- 把类加载、链接和初始化混成一个动作。
- 没有隔离需求却采用子优先加载，制造依赖冲突和安全风险。

## Q7：InnoDB 为什么用 B+Tree，而不是 B 树或红黑树？

**短回答：**

结论：B+Tree 的高扇出降低磁盘层数，叶子按键有序并保存行或主键，既适合点查也适合范围扫描；选择核心是页 I/O，而不是“树越平衡越好”。

**原理：**

InnoDB 以固定大小页组织索引。非叶子节点主要保存键与子页指针，同一页能容纳更多分支，使大数据量下根到叶通常只需少数页访问；叶子节点有序，范围查询定位起点后可连续扫描。红黑树每节点分支少，数据量大时层数高且对象式节点不匹配页存储。普通 B 树在内部节点也存记录，降低扇出。真实性能还受缓存池、键宽、页分裂和回表影响。

![InnoDB B+Tree 内部节点、叶子页与范围扫描关系图](/content/diagrams/database-cache/b-plus-tree-v1.svg "内部节点负责导航，数据集中在有序叶子页，使点查与范围扫描兼顾较少随机 I/O。")

**代码 / 场景：**

一亿行订单按 `(user_id, created_at)` 查询最近记录，联合 B+Tree 可先定位用户范围，再顺序扫描时间段。设计前用 EXPLAIN 验证 key、rows 与访问类型，并通过冷缓存/热缓存两组压测区分 I/O 与 CPU。

**递进追问：**

1. **Hash 索引为什么不适合通用范围查询？**

   哈希只便于等值定位，不保持键的全序，无法直接支持范围、排序和最左前缀扫描。

2. **B+Tree 层数少就一定快吗？**

   不一定，选择度差、回表多、随机页读和锁等待仍可能成为主要瓶颈。

**易错点：**

- 只回答“B+Tree 矮”，没有解释页、扇出和范围扫描。
- 把索引结构优势当成任意 SQL 都会自动高效。

## Q8：聚簇、二级与覆盖索引如何决定是否回表？

**短回答：**

结论：InnoDB 聚簇索引叶子保存整行，二级索引叶子保存索引列和主键；查询列能由二级索引直接提供时形成覆盖索引，否则需按主键回表。

**原理：**

每张 InnoDB 表的数据按聚簇索引组织，通常使用主键；二级索引找到候选后携带主键值，再访问聚簇树取得其余列。覆盖索引避免第二次树查找与随机页访问，但会增加索引宽度和写放大。主键越宽，所有二级索引叶子携带的主键也越宽。优化不能只看“用了索引”，还要看扫描行数、回表次数、过滤比例以及是否发生排序。

**代码 / 场景：**

查询 `SELECT created_at,status FROM orders WHERE user_id=? ORDER BY created_at DESC LIMIT 20`，可评估 `(user_id, created_at, status)` 覆盖；若 status 更新极频繁，宽索引写成本可能不划算。用 EXPLAIN 与 Handler 统计验证扫描和回表。

**递进追问：**

1. **覆盖索引为什么不等于索引越宽越好？**

   更多列会占用磁盘和缓存、降低页扇出并放大插入更新成本，需要以高频查询收益换算。

2. **二级索引叶子为什么保存主键？**

   它既用于同值记录的唯一定位，也能作为访问聚簇索引整行数据的回表地址。

**易错点：**

- 把二级索引叶子说成直接保存整行所有列。
- 为消除一次回表把大量低价值列全部塞进索引。

## Q9：联合索引在数据倾斜时仍会遵守最左匹配吗？

**短回答：**

结论：索引键顺序不会因某列取值都相同就自动跳过最左列；优化器是否选择索引取决于可用访问路径和成本，不能用数据内容替代索引前缀规则。

**原理：**

联合 B+Tree 先按第一列排序，再在相同第一列范围内按第二列排序。缺少最左列条件时，第二列在全树上不是一个连续全局区间，常无法直接做普通范围定位；某些版本和场景可能使用 skip scan 等优化，但这是成本选择，不是索引定义改变。范围条件后的后续列通常不能继续缩小定位区间，却可能用于索引条件下推过滤。统计信息失真时，优化器还可能选错路径。

**代码 / 场景：**

索引 `(tenant_id,status,created_at)` 若所有历史数据 tenant_id 暂时相同，仍应在 SQL 明确租户条件；否则未来多租户后计划会恶化。用不同数据分布执行 EXPLAIN ANALYZE，验证实际行数与估算差异。

**递进追问：**

1. **范围条件后的列完全没用吗？**

   不一定，它可能不再参与连续索引定位，但仍可用于索引条件下推、覆盖或避免回表过滤。

2. **为什么同一 SQL 有时突然不走索引？**

   数据分布、统计信息、参数值和缓存成本变化都可能让优化器判断全表扫描更便宜。

**易错点：**

- 把偶然常量列当作优化器自动改写索引顺序的依据。
- 只看 possible_keys，不核对最终 key 和实际扫描行。

## Q10：MySQL 与 Elasticsearch 深分页分别怎样改写？

**短回答：**

结论：大 offset 会读取并丢弃前面大量结果；连续翻页优先使用稳定排序键做 seek/search_after，必须跳页时才接受更高成本或改产品交互。

**原理：**

MySQL `LIMIT offset,size` 需要找到并跳过 offset 条，二级索引查询还可能为大量候选回表；可先在窄覆盖索引中定位主键再关联，或用上一页 `(sort_key,id)` 作为下一页边界。Elasticsearch 每个分片都要准备 `from + size` 候选并在协调节点归并，深页会放大堆与 CPU；search_after 配合 point in time 能保持分页视图。所有方案都需要唯一稳定的二级排序键，防止并列值漏项或重复。

**代码 / 场景：**

订单列表按 `created_at DESC,id DESC` 返回游标，下一页条件写成“小于上页末尾二元组”；ES 同样以这两个 sort 值 search_after。用百万级数据验证第 1 页与第 10000 页延迟、重复率和写入并发下的一致性。

**递进追问：**

1. **seek 分页为什么难以直接跳到任意页？**

   它依赖上一页末尾边界，没有中间游标就不知道目标页起点，这是用交互能力换稳定性能。

2. **只按时间排序会有什么问题？**

   多个记录时间相同会导致边界不唯一，需要追加主键等唯一列形成确定顺序。

**易错点：**

- 把子查询优化当成所有深分页场景的固定答案。
- 游标排序键不唯一，导致并发数据下重复或遗漏。

## Q11：MVCC 如何让可重复读看到稳定快照？

**短回答：**

结论：InnoDB 通过隐藏事务信息、undo 版本链和一致性读视图判断哪个版本可见；它减少读写阻塞，但当前读仍需锁，不能把 MVCC 等同于无锁事务。

**原理：**

记录修改会保留指向旧版本的 undo 信息，一致性读根据 Read View 中活跃事务边界判断当前版本是否可见，不可见则沿版本链回溯。可重复读事务通常复用一致性快照，使同一记录多次快照读保持稳定；读已提交会为每个语句取得更新视图。`SELECT ... FOR UPDATE`、UPDATE 和 DELETE 属于当前读，读取最新可锁版本并参与行锁/间隙锁协议。长事务会阻碍旧版本清理并扩大 undo。

**代码 / 场景：**

对账任务在可重复读事务中先后两次普通 SELECT 得到同一快照，但中间若使用 FOR UPDATE，语义转为当前读。测试用两个连接按时间线提交更新，记录每个语句结果并检查 history list length，避免长事务拖累清理。

**递进追问：**

1. **MVCC 能避免所有幻读吗？**

   快照读可保持视图稳定；当前读要依靠锁范围控制，不能只靠版本链。

2. **长只读事务为什么也可能有成本？**

   它持有较老视图，使 purge 不能清理仍可能被该视图访问的 undo 版本。

**易错点：**

- 把 Read View 说成复制整张表的物理快照。
- 忽略快照读与当前读的语义差异。

## Q12：Next-Key Lock、redo、undo 与 binlog 各解决什么？

**短回答：**

结论：Next-Key Lock 保护索引记录及相邻间隙的并发范围，redo 保证崩溃恢复，undo 支持回滚和旧版本，binlog 服务逻辑复制与审计；四者职责不能互换。

**原理：**

InnoDB 当前读按实际索引访问路径加记录锁、间隙锁或二者组合的 Next-Key Lock，精确唯一索引等值命中时可能缩小范围。redo 是存储引擎物理恢复日志，事务提交按刷盘策略获得持久性；undo 保存反向操作/旧版本信息；binlog 位于服务器层，记录逻辑变更供复制与恢复。提交需协调存储引擎与 binlog，避免一边成功另一边缺失。锁范围则要通过索引和隔离级别具体分析。

**代码 / 场景：**

库存表按非唯一 status 范围更新时，锁可能覆盖多个记录和间隙，阻塞新插入；补充更精确索引可缩小扫描与锁范围。故障测试应在提交阶段杀进程，恢复后核对数据、redo 与 binlog 位点一致。

**递进追问：**

1. **间隙锁是否锁住一条真实记录？**

   它保护的是索引键之间的区间，主要阻止该间隙插入，并不等同于锁定某条已有行。

2. **有 binlog 为什么还需要 redo？**

   binlog 面向逻辑复制，redo 面向 InnoDB 页级崩溃恢复，记录层次和恢复目标不同。

**易错点：**

- 脱离索引访问路径背诵固定锁范围。
- 把 undo、redo、binlog 都泛称为“事务日志”而不分职责。

## Q13：Redis 的高吞吐来自哪些条件，瓶颈又在哪里？

**短回答：**

结论：内存访问、紧凑数据结构、事件驱动 I/O 和短命令执行共同带来高吞吐；单线程命令路径避免锁竞争，但慢命令、网络、持久化和大 Key 仍会阻塞。

**原理：**

Redis 通过事件循环监听大量连接，就绪后读取请求并执行命令；核心数据在内存，常规操作减少磁盘随机 I/O。单命令串行执行简化原子性，却意味着 `KEYS`、大集合删除、复杂 Lua 或巨大响应可占住执行线程。后台线程与子进程会承担部分 I/O、释放或持久化工作，但不能把 Redis 简化成“完全单线程”。性能分析应拆成客户端排队、网络、命令耗时、fork/写时复制和内存压力。

**代码 / 场景：**

缓存 p99 突然升高时，先检查 slowlog、latency doctor、大 Key、网络与持久化事件；若发现线上 `KEYS *`，改为受控 SCAN 并限制批量。用真实 value 尺寸压测，不能只用小 key 得出容量结论。

**递进追问：**

1. **单线程为什么还能处理很多连接？**

   I/O 多路复用让一个事件循环只处理已就绪连接，避免为每个空闲连接阻塞一个线程。

2. **Lua 脚本原子是否代表可以无限执行？**

   不代表，长脚本会阻塞其他命令，应限制复杂度和处理数据量。

**易错点：**

- 只回答“因为内存”，遗漏事件循环、数据结构和阻塞风险。
- 把所有后台工作也错误描述为单线程。

## Q14：Redis 数据结构怎样按访问模式选，ZSet 为何使用跳表？

**短回答：**

结论：选择应从读写命令和容量出发；ZSet 需要同时支持成员去重、按分值定位与范围遍历，字典加跳表正好覆盖等值和有序操作。

**原理：**

String 适合计数、位图和简单值，Hash 适合对象字段，List 适合有序两端操作，Set 适合无序去重，ZSet 适合排行榜与区间。跳表通过多级随机索引把期望查找、插入、删除降到 O(log n)，底层链表又便于顺序范围扫描；字典从 member 快速找到 score。结构选择还要考虑编码转换、大元素数量、单 key 热点及跨槽操作限制。

**代码 / 场景：**

实时积分榜以用户 ID 为 member、积分为 score，用 ZADD 更新、ZREVRANGE 取榜；若只需判断是否参与活动，Set 更简单。压测应覆盖百万 member 下的更新与 Top-N，并监控单 key CPU 和内存。

**递进追问：**

1. **跳表为什么不用严格平衡树？**

   随机层级实现简单，期望复杂度稳定，且底层有序链天然适合连续范围遍历。

2. **排行榜拆成多个 key 会有什么代价？**

   可分散热点，但全局 Top-N 需要额外归并，并要处理分片更新一致性。

**易错点：**

- 按数据名字选结构，不先定义具体命令与访问频率。
- 把所有用户塞进单个超大 ZSet，却不评估热点与迁移。

## Q15：RDB、AOF 与淘汰策略怎样组合成可恢复缓存？

**短回答：**

结论：RDB 提供紧凑快照，AOF 记录写命令并可配置刷盘；淘汰策略只处理达到内存上限后的 key 选择。三者需按允许丢失量与缓存角色共同配置。

**原理：**

RDB 在时间点生成数据快照，恢复快但两次快照间变更可能丢失；AOF 追加写操作，按 always/everysec/no 等策略权衡持久性与延迟，并需重写控制体积。达到 maxmemory 后，noeviction 会拒绝写，LRU/LFU/TTL/随机策略则在全部 key 或带过期 key 范围选择淘汰。持久化不是高可用，副本也可能复制错误删除；权威数据仍需有明确事实来源。

**代码 / 场景：**

会话若必须跨 Redis 故障保留，不应只依赖缓存淘汰策略，可使用 AOF everysec 加副本并在数据库保留关键状态。故障演练杀主节点，记录已确认写的丢失窗口、恢复时间与被淘汰 key 类型。

**递进追问：**

1. **AOF everysec 能保证零丢失吗？**

   不能，故障窗口内仍可能丢失尚未刷盘的数据，只是将常见窗口控制在约秒级。

2. **allkeys-lru 是精确全局 LRU 吗？**

   Redis 使用近似采样策略控制成本，不能把淘汰顺序当作严格全局排序。

**易错点：**

- 把副本、持久化和备份当作同一层保障。
- 未设置 maxmemory 就讨论淘汰策略，导致实例最终受系统 OOM 控制。

## Q16：缓存穿透、击穿和雪崩如何按失败形态分别治理？

**短回答：**

结论：穿透是不存在数据反复回源，击穿是单个热点失效瞬间并发回源，雪崩是大量 key 或缓存服务同时失效；三者的检测指标和治理手段不同。

**原理：**

穿透可对合法不存在结果做短负缓存、参数校验或 Bloom Filter，但要处理误判和数据新建后的失效；击穿可用请求合并、逻辑过期、互斥重建和热点预热，并确保锁等待有上限；雪崩需让 TTL 加抖动、分批预热、缓存集群高可用，同时保护数据库连接池并提供降级。所有方案都要防缓存重建失败，否则互斥锁只会把并发洪峰变成长时间排队。

**代码 / 场景：**

热门商品 key 到期时只允许一个加载协程回源，其余请求短等后读取新值或返回旧值；不存在商品缓存 30 秒并在创建事件后主动删除。演练同时过期一万 key，观察回源 QPS、等待和降级比例。

**递进追问：**

1. **Bloom Filter 为什么不能单独做最终判断？**

   它可能误判存在且不保存真实值，只适合作前置过滤，最终结果仍由事实存储确认。

2. **互斥重建失败后应如何处理？**

   锁要有超时，加载失败应释放并限速重试，同时允许旧值、负缓存或降级响应兜底。

**易错点：**

- 把三种问题都回答成“加锁”，没有区分流量形态。
- 所有 key 使用同一固定 TTL，主动制造集中失效。

## Q17：Redisson 风格的续期锁怎样处理误删与进程崩溃？

**短回答：**

结论：锁值必须标识持有者，释放用原子比较删除；续期只能延长仍由自己持有的锁，进程崩溃后则靠租约最终过期，不能无限续命。

**原理：**

客户端以唯一 token 获取带 TTL 的 key，成功后定时检查持有关系并延长租约。解锁必须在一个 Lua 脚本中比较 token 后删除，避免旧持有者超时后误删新持有者的锁。续期线程随进程死亡而停止，TTL 到期允许其他实例恢复。网络暂停、主从切换和 GC 停顿可能让锁实际过期但旧任务继续执行，因此仅有 Redis 锁不能阻止迟到写；关键资源需要 fencing token 或存储层版本检查。

**代码 / 场景：**

账单生成任务获取锁时同时获得递增 fencing 版本，数据库只接受不小于当前版本的写入。故障注入暂停旧进程超过 TTL，再让新进程接管，恢复旧进程后确认其写入被版本条件拒绝。

**递进追问：**

1. **为什么不能直接 DEL 锁 key？**

   旧持有者的租约可能已过期且新持有者已加锁，直接删除会误删别人的有效锁。

2. **Watchdog 能解决所有超时问题吗？**

   不能，长暂停或网络分区仍可能失去租约，外部资源需要 fencing 或幂等约束。

**易错点：**

- 只设置过期时间，不校验锁拥有者就删除。
- 把续期锁当作跨系统强一致事务，遗漏迟到写。

## Q18：Redis 主从切换期间怎样理解复制顺序与可用性？

**短回答：**

结论：单连接命令按复制流顺序应用，但复制通常是异步的；主节点确认写后立刻故障，未到副本的数据可能丢失，故不能据此宣称线性一致。

**原理：**

副本建立连接后进行全量或部分同步，随后持续接收主节点命令流。复制偏移量用于判断断线后能否部分续传；链路内顺序不代表跨客户端全局线性化，也不保证已返回写必然落到晋升副本。故障转移在可用性与数据新鲜度间取舍，客户端还要处理旧主恢复、读副本延迟和拓扑变更。Cluster 分片进一步要求理解槽迁移与多 key 限制。

**代码 / 场景：**

写入订单状态后若立即从副本读取，可能读到旧值；关键读可走主库或携带版本等待副本追平。故障演练在持续写入时隔离主节点，统计成功响应中有多少未出现在新主，并核对复制 offset。

**递进追问：**

1. **副本按顺序执行为何仍会读旧数据？**

   因为异步传输存在延迟，顺序只约束已收到命令的应用次序，不保证已经追到主节点最新位置。

2. **WAIT 命令是否等于强一致提交？**

   它可等待指定副本确认以降低丢失概率，但仍不等同于完整共识协议和绝对持久性。

**易错点：**

- 把“复制有序”推导成所有读写都线性一致。
- 只验证正常同步，不演练主从切换中的已确认写丢失窗口。

# JVM、GC 与生产诊断

## Q19：一次 Java 方法调用会使用哪些 JVM 运行时数据区？

**短回答：**

结论：线程执行方法主要使用自己的程序计数器和虚拟机栈，实例通常分配在共享堆，类结构与运行时常量由方法区语义承载；各区域的生命周期和故障不同。

**原理：**

每个线程拥有程序计数器和栈，每次方法调用创建栈帧，保存局部变量、操作数栈、动态链接与返回信息；本地方法还涉及本地方法栈的实现。堆由线程共享，是垃圾回收重点。方法区是规范概念，HotSpot 现代实现以 Metaspace 承载类元数据，但“方法区等于永久代”并不成立。对象逃逸分析可能允许标量替换，所以“所有对象一定在堆上”也不应作为绝对结论。

**代码 / 场景：**

递归接口不断创建栈帧更可能触发 StackOverflowError；动态生成大量代理类且类加载器无法卸载，更可能推高 Metaspace；业务对象引用链未释放则表现为堆持续增长。排障先按异常类型与区域指标分类，再抓对应证据。

**递进追问：**

1. **局部变量一定存放在栈上吗？**

   局部变量槽位在栈帧中，但引用指向的对象位置由运行时决定，优化后还可能被标量替换。

2. **方法区和 Metaspace 是同一个概念吗？**

   方法区是 JVM 规范定义的逻辑区域，Metaspace 是 HotSpot 对其中类元数据的一种实现。

**易错点：**

- 把 JMM 的主内存/工作内存与 JVM 运行时数据区混为一谈。
- 断言所有 new 出来的对象永远以完整对象形式位于堆中。

## Q20：可达性分析怎样处理循环引用并决定对象生死？

**短回答：**

结论：主流 JVM 从 GC Roots 沿引用图标记可达对象，两个对象即使互相引用，只要整体不再从根可达，仍可被回收，因此不会被简单引用计数困住。

**原理：**

GC Roots 可包括活动线程栈中的引用、类静态字段、JNI 引用等实现规定的根集合。回收器在安全点或并发标记协议下遍历对象图；强引用保持可达，软、弱、虚引用具有不同清理语义。对象从“不可达”到实际内存回收仍可能跨越引用处理、终结相关兼容行为和清扫阶段，所以不能用一次 System.gc() 断言回收完成。业务正确性也不应依赖 finalize。

**代码 / 场景：**

监听器注册到长生命周期单例后，即使页面对象之间没有业务引用，单例仍从根持有它们，形成真实泄漏；两个临时对象互相引用却都不再连接根则不是泄漏。可用堆转储查看到 GC Root 的最短引用链来验证。

**递进追问：**

1. **弱引用适合直接做关键业务缓存吗？**

   通常不适合，回收时机受内存压力影响且不可预测，关键数据需要明确容量、过期和重建策略。

2. **System.gc() 能保证立即回收指定对象吗？**

   不能，它最多表达一次建议，具体是否执行、何时执行和回收哪些对象由 JVM 策略决定。

**易错点：**

- 把互相引用直接判定为无法回收的内存泄漏。
- 用 finalize 或 System.gc() 作为资源释放与测试断言。

## Q21：CMS、G1 与低停顿收集器的选择依据是什么？

**短回答：**

结论：选择收集器应围绕堆规模、暂停目标、吞吐和 JDK 支持版本；G1 以 Region 和可预测暂停为主，低停顿收集器用更多并发工作换取更短停顿。

**原理：**

CMS 以老年代并发标记清除降低停顿，但会产生碎片，并存在并发失败等维护成本；现代 JDK 已移除它。G1 将堆划分为 Region，统一处理年轻代和老年代，通过 remembered set 跟踪跨区引用，按收益选择回收集合。ZGC、Shenandoah 将更多标记、重定位工作并发化，适合大堆低停顿目标，但仍要评估 CPU、内存余量和应用分配速率。任何收集器都无法弥补无界对象增长。

**代码 / 场景：**

延迟敏感 API 从 Parallel GC 迁移 G1 时，先记录基线吞吐、p99、分配率和 Full GC 原因，再设定可验证暂停目标并做相同流量回放。若堆持续占满，应先修复存活集或容量问题，而不是反复更换收集器。

**递进追问：**

1. **G1 为什么能做暂停预测？**

   它维护各 Region 回收成本与收益估计，在暂停预算内选择一组回收集合，但预测并非绝对保证。

2. **低停顿是否意味着吞吐一定更高？**

   不意味着，并发标记和转移会消耗 CPU 与内存带宽，通常需要用部分吞吐换更短暂停。

**易错点：**

- 在现代 JDK 题目中仍把 CMS 当作默认可用方案。
- 只背收集器名称，不给堆规模、暂停 SLO 和验证指标。

## Q22：线上内存泄漏如何证明是存活集增长而非正常缓存？

**短回答：**

结论：先看 Full GC 后基线是否持续上升，再用类直方图、堆转储和 GC Root 引用链定位增长对象；缓存命中高也不能替代容量与回收证据。

**原理：**

泄漏是对象已无业务价值却仍被引用，常见来源包括静态集合、监听器、ThreadLocal、未关闭类加载器和无界缓存。排查先关联堆使用、GC 频率、分配率和请求负载，确认不是流量增长造成的合理工作集；再多时点采集 class histogram 比较实例与字节增量，必要时转储堆分析 dominator 与到根路径。转储可能造成停顿和敏感数据暴露，需选择副本、限流或离线环境。

**代码 / 场景：**

若用户会话缓存从不淘汰，Full GC 后 retained heap 仍随用户数单调上涨。先用 `jcmd GC.class_histogram` 比较增长类，再在受控实例生成 heap dump，找到静态 Map 到会话对象的路径；修复后以固定流量跑足过期周期，确认基线回落。

**递进追问：**

1. **堆使用上涨就一定是泄漏吗？**

   不一定，扩容后的正常存活集、批任务和缓存预热都会上涨，关键看负载归零和回收后是否回落。

2. **为什么不能直接在所有生产实例 dump？**

   堆转储可能触发停顿、磁盘压力并包含敏感数据，应控制实例、权限、时间与留存。

**易错点：**

- 只看瞬时堆曲线，不比较 Full GC 后基线和业务负载。
- 未经评估在高峰生成巨大 heap dump，造成二次事故。

## Q23：发版重启导致本地缓存丢失时如何避免流量击穿？

**短回答：**

结论：本地缓存应被视为可丢失加速层，重启恢复要靠分批发布、预热、请求合并、限流和下游容量保护，不能把内存内容当唯一事实来源。

**原理：**

进程重启后冷缓存会把命中流量瞬间转移到数据库或远端服务，多实例同时发布会形成同步冲击。发布系统应限制并发下线数，健康检查不仅看端口，还应在关键缓存达到最低可服务状态后接流量。热点可从持久来源异步预热；未命中时使用 single-flight 合并同键加载，并设置超时、负缓存与最大并发。回滚同样是一次冷启动，必须进入容量模型。

**代码 / 场景：**

商品详情服务发布前导出热点 key 清单，新实例启动后限速预热前一万条；达到命中率阈值再加入负载均衡。压测同时重启一个批次，确认数据库 QPS、连接池等待和错误率不越界，并演练预热失败后的降级页面。

**递进追问：**

1. **把缓存序列化到本地磁盘就足够了吗？**

   不够，磁盘快照可能过期、损坏或与新版本结构不兼容，只能作加速且需版本校验。

2. **为什么发布批次也要进入缓存设计？**

   因为同时失去多少缓存实例直接决定回源峰值，是系统容量而非单纯运维问题。

**易错点：**

- 把本地缓存当权威数据，重启后无法从事实来源恢复。
- 所有实例同时滚动且同时预热，把预热本身变成攻击流量。

## Q24：4GB 物理内存的机器申请 8GB 时系统会怎样处理？

**短回答：**

结论：申请的是虚拟地址空间，不等于立即占用同量物理内存；结果取决于进程位数、提交策略、页实际触达、交换空间、容器限制和内核过量承诺。

**原理：**

虚拟内存把进程地址映射到物理页或后备存储，匿名映射常在首次触达页面时按需分配。64 位进程通常有足够地址空间保留 8GB，但实际写满时可能频繁换页、触发内存回收或被 OOM killer 终止；32 位进程往往先受用户地址空间上限限制。Linux overcommit 还可能让申请先成功、后续缺页时失败。容器 cgroup 限额可能比宿主机物理内存更早成为边界。

**代码 / 场景：**

Java 服务把 `-Xmx8g` 部署到 4GB 限额容器，即使启动成功，堆提交和堆外内存叠加后仍可能被杀。验证需同时看进程虚拟/常驻内存、page fault、swap、cgroup memory.events 与内核日志，而不是只看 malloc 返回值。

**递进追问：**

1. **虚拟内存很大是否代表可以放心使用？**

   不代表，地址保留不等于物理容量，实际触达仍受 RAM、swap、限额和延迟目标约束。

2. **32 位与 64 位差异只有指针大小吗？**

   不是，最关键还包括可寻址空间上限，此外对象布局、ABI 与页表开销也会变化。

**易错点：**

- 把申请成功误认为 8GB 物理页已经全部分配。
- 只讨论宿主机内存，忽略容器 cgroup 与 JVM 堆外占用。

## Q25：Spring Bean 从定义到可调用代理经历哪些阶段？

**短回答：**

结论：容器先读取 BeanDefinition，再实例化、注入依赖、执行 Aware 与后处理器、初始化回调；需要 AOP 时，最终暴露给调用方的可能是代理而非原对象。

**原理：**

BeanDefinition 保存类、作用域、构造参数和生命周期元数据。容器创建实例后填充属性，调用相关 Aware 接口，再依次经过 BeanPostProcessor 的初始化前后回调；`@PostConstruct`、InitializingBean 或自定义 init 方法在规定阶段执行。代理通常由后处理器在初始化后包装。单例缓存的是容器管理的最终引用，销毁时再调用回调。构造器里访问尚未注入的依赖或启动外部线程，会破坏生命周期假设。

**代码 / 场景：**

审计切面 Bean 在构造器里调用自身业务方法时，调用发生在代理完成前，不会经过切面。应把外部连接建立放到明确初始化阶段，并用集成测试从容器取 Bean 调用，验证实际类型、切面与销毁回调。

**递进追问：**

1. **BeanPostProcessor 与 BeanFactoryPostProcessor 区别是什么？**

   前者处理 Bean 实例，后者在实例化前修改 BeanDefinition 等容器元数据。

2. **prototype Bean 会自动执行销毁回调吗？**

   容器通常不管理其完整销毁生命周期，调用方需负责释放 prototype 实例持有的资源。

**易错点：**

- 把实例化和依赖注入说成同一个瞬间。
- 在构造器中依赖尚未完成的代理、事务或外部资源。

## Q26：Spring AOP 何时使用 JDK 代理，何时使用类代理？

**短回答：**

结论：面向接口可使用 JDK 动态代理，类代理通过生成子类拦截可覆盖方法；两者都只能拦截经过代理引用的调用，不能把对象内部自调用自动变成切面调用。

**原理：**

代理对象持有目标对象与拦截器链，调用进入代理后按顺序执行事务、日志等 Advice，再反射或方法句柄调用目标。JDK 代理暴露接口类型；类代理需要目标类可继承、方法可覆盖，因此 final 类或 final/private 方法无法按普通子类方式增强。Spring 可根据配置和目标类型选择代理。代理只在容器边界生效，`this.method()` 没有重新经过代理。

**代码 / 场景：**

订单服务接口由控制器注入代理，外部调用能记录审计日志；同类方法 A 直接调用方法 B 时，B 上的独立切面可能不生效。可将 B 抽到另一个 Bean，或重新设计事务边界，并在测试中检查代理类型与切面计数。

**递进追问：**

1. **private 方法为什么难以被常规 Spring AOP 拦截？**

   它不能被子类覆盖，也不会通过接口代理暴露，普通代理调用链无法在其入口接管。

2. **代理与 AspectJ 编织有何边界差异？**

   代理主要拦截对象边界的方法调用，编织可修改字节码连接点，但部署和调试复杂度更高。

**易错点：**

- 认为加了注解就能拦截任何 private、final 或自调用。
- 调用方持有手工 new 的原对象，却期待容器代理生效。

## Q27：Spring 单例循环依赖为什么有时能解、有时不能？

**短回答：**

结论：部分属性/Setter 注入的单例循环依赖可借助提前暴露引用解决；构造器循环在任一实例尚未创建前就互相等待，无法用同一机制补全。

**原理：**

创建单例 A 后、属性填充前，容器可登记一个获取其早期引用的工厂；创建依赖 B 时若 B 又需要 A，可取早期引用继续完成 B，再回填 A。若 A 最终需要 AOP，早期引用必须与最终暴露代理保持一致，否则会出现原对象和代理不一致。prototype 不由单例缓存统一管理，也无法套用该流程。即使容器能解开，双向依赖通常反映职责耦合，应优先重构。

**代码 / 场景：**

订单服务与库存服务互相注入时，不要依赖“三级缓存能跑”；提取库存预占协调器，由其单向调用两个领域服务。测试同时覆盖启用事务代理后的 Bean 身份，避免一侧拿到原对象绕过切面。

**递进追问：**

1. **为什么构造器循环不能提前暴露？**

   构造 A 必须先得到 B，而构造 B 又必须先得到 A，此时两个完整实例都尚未产生可供回填。

2. **能自动启动就代表设计合理吗？**

   不代表，循环依赖增加初始化顺序和代理一致性风险，应视为需要审查的架构信号。

**易错点：**

- 把所有循环依赖都归结为“三级缓存一定解决”。
- 只为消除启动错误改成字段注入，却保留领域职责环。

## Q28：Spring 事务传播与常见失效路径怎样一起解释？

**短回答：**

结论：声明式事务通过代理拦截方法并绑定线程资源；传播行为决定已有事务下加入、挂起或创建保存点，失效常源于调用未经过代理或异常未越过边界。

**原理：**

外部调用代理方法时，事务拦截器根据属性取得事务管理器，开启或复用事务，目标成功则提交，匹配回滚规则的异常则回滚。REQUIRED 加入当前事务，REQUIRES_NEW 挂起外层并创建新事务，NESTED 通常依赖保存点且受管理器能力限制。自调用、对象不在容器、方法不可代理、异常被吞掉、异步切换线程或受检异常未配置 rollbackFor，都可能使预期与实际不同。

**代码 / 场景：**

批量导入中主事务调用同类 `saveItem()`，即使后者标了 REQUIRES_NEW 也可能没有新事务。将单项写入放到独立 Bean，经代理调用，并故障注入第三条写入异常，核对数据库提交边界和事务日志。

**递进追问：**

1. **REQUIRES_NEW 一定更安全吗？**

   不一定，它会增加独立连接占用，并可能留下外层失败、内层已提交的业务补偿问题。

2. **异步线程会继承当前事务吗？**

   通常不会，事务资源多绑定在线程上下文，新线程需要自己的事务边界或消息一致性方案。

**易错点：**

- 只背传播枚举，不说明已有事务存在时具体发生什么。
- 在方法内捕获异常后正常返回，却期待代理自动回滚。

## Q29：一次 Dubbo 调用从代理到 Provider 经历什么？

**短回答：**

结论：消费者调用本地代理后，框架把方法与参数封装为调用，经过过滤器、目录、路由、负载均衡和集群容错选出 Invoker，再通过协议与网络客户端发送到 Provider。

**原理：**

Provider 启动时导出服务并向注册中心登记可发现信息；Consumer 订阅地址和配置，创建引用代理。调用进入代理后形成 Invocation，Filter 链可处理上下文、超时和监控，Directory 提供候选 Invoker，Router 过滤，LoadBalance 选择节点，Cluster 策略决定失败重试或快速失败。网络层完成序列化、请求 ID 关联和响应解码。重试只适合幂等操作，超时也不表示服务端一定未执行。

**代码 / 场景：**

**递进追问：**

1. **注册中心短暂不可用，已有调用一定失败吗？**

2. **RPC 超时后为何仍要考虑幂等？**

- 对非幂等写操作开启无条件自动重试。

## Q30：注册中心故障和网络分区时服务发现如何降级？

# JMM、线程池与锁

## Q31：JMM 怎样解释可见性、有序性与 happens-before？

**短回答：**

结论：JMM 不是 JVM 内存区域图，而是线程间读写共享变量的规则；happens-before 给出“前一动作结果必须对后一动作可见”的最低保证。

**原理：**

每个线程可能从寄存器或缓存使用共享变量副本，编译器与处理器也可在不破坏单线程语义时重排。程序次序、监视器解锁到后续加锁、volatile 写到后续读、线程 start/join 等规则建立 happens-before；该关系还具有传递性。没有这条关系的竞态读写结果不受业务直觉保护。原子性、可见性和有序性是不同维度，volatile 只覆盖其中部分。

**代码 / 场景：**

配置热更新时，先完整构造不可变配置对象，再写入 volatile 引用；工作线程读取同一引用后可看到构造完成的字段。验证可用 JCStress 或大量并发测试寻找旧值，但“没复现”不能证明无数据竞争，还需代码层建立明确同步边。

**递进追问：**

1. **volatile 写读建立了什么保证？**

   对同一变量的写 happens-before 后续读，写前普通写入也可经传递关系对读线程可见。

2. **happens-before 是否等于真实时间上先执行？**

   不等于，它描述内存可见性与允许的执行结果，不要求所有动作按墙钟时间完全串行。

**易错点：**

- 把 JMM 误画成堆、栈、方法区的内存分区。
- 只说“禁止重排”，不说明针对哪类读写建立可见性。

## Q32：volatile 为什么不能让 i++ 变成原子操作？

**短回答：**

结论：volatile 保证读写可见性并约束部分重排，但 `i++` 包含读取、计算、写回三个动作，多个线程仍可能读取同一个旧值并覆盖更新。

**原理：**

对 volatile 变量的单次读写具有规定的同步语义，却不会把复合表达式自动包装为不可分割事务。两个线程都读到 10，各自计算 11 并写回，最终只增加一次。计数需求可用 AtomicLong 的 CAS 循环、LongAdder 的分散累加，或在更大不变量上使用锁；选择取决于是否要求线性化读取、竞争强度及是否需要把多个字段一并更新。

**代码 / 场景：**

接口请求总量只用于监控且高并发时可使用 LongAdder；库存余量要求每次扣减可线性化并联动订单状态时，不能只换原子计数器，应在数据库条件更新或事务边界内完成。通过并发屏障同时执行一百万次自增，核对期望值与实际值。

**递进追问：**

1. **AtomicLong 与 LongAdder 如何选择？**

   AtomicLong 提供单值 CAS 与精确瞬时读取；LongAdder 高竞争吞吐更好，但 sum 不是全局线性化快照。

2. **volatile 能安全发布对象吗？**

   先完成对象构造再写入 volatile 引用，可以借助写读关系安全发布其构造前状态。

**易错点：**

- 把可见性直接等同于复合操作原子性。
- 在要求强一致余额的路径上用 LongAdder 追求吞吐。

## Q33：CAS、AQS 与公平锁之间是什么关系？

**短回答：**

结论：CAS 是条件更新原语，AQS 用原子状态和等待队列搭建同步器；公平性由获取策略决定，不是 CAS 本身天然提供的属性。

**原理：**

CAS 比较内存当前值与期望值，相等才写入新值，失败方可重试、入队或返回。AQS 维护 volatile state，并把竞争失败的线程组织为队列节点；独占或共享模式由子类定义 tryAcquire/tryRelease 语义。公平锁获取前会尊重队列中是否已有前驱，非公平锁允许新线程抢占，常有更高吞吐但可能增加尾延迟。高竞争下无界自旋会浪费 CPU，因此同步器需在自旋与挂起间权衡。

**代码 / 场景：**

连接池许可可基于 Semaphore 的共享模式；需要严格排队的人工审批任务可评估公平锁，但普通短临界区先用非公平锁并测量 p99。验证记录获取顺序、阻塞时间和 CPU，自旋成功率不能只看平均吞吐。

**递进追问：**

1. **CAS 的 ABA 问题是什么？**

   值从 A 变 B 又变 A 时普通 CAS 看不出中间变化，可用版本戳、不可复用节点或更高层协议处理。

2. **AQS 队列是否就是业务任务队列？**

   不是，它保存等待同步状态的线程节点，不负责承载线程池中的业务 Runnable。

**易错点：**

- 把 CAS 描述成完全没有开销的无锁万能方案。
- 把公平锁理解为绝对墙钟顺序，忽略调度和取消等因素。

## Q34：synchronized 与 ReentrantLock 的取舍怎样结合锁升级说明？

**短回答：**

结论：两者都能建立互斥和可见性；synchronized 语法简单且自动释放，ReentrantLock 提供可中断、超时、公平及多条件队列，选择应由控制需求决定。

**原理：**

进入和退出 synchronized 监视器形成 happens-before，并由 JVM 管理异常释放。JVM 可针对竞争形态使用轻量路径、自旋或膨胀到重量级监视器，这属于实现优化，业务代码不应依赖固定升级细节。ReentrantLock 基于 AQS，必须在 finally 中 unlock，可通过 tryLock 限时退让，Condition 将不同等待条件分组。两者都不能修复锁范围过大或锁顺序不一致。

**代码 / 场景：**

账户间转账若必须拿两把锁，应先按账户 ID 排序，避免循环等待；如果外部调用可能长时间阻塞，可用 tryLock 超时后回滚并重试。验证应做故障注入，让临界区抛异常，确认锁一定释放且无部分更新。

**递进追问：**

1. **synchronized 锁能主动降级吗？**

   业务 API 没有主动降级能力；JVM 的具体锁状态优化属于实现细节，不应作为正确性前提。

2. **什么时候需要多个 Condition？**

   同一锁保护多种等待谓词时可分别唤醒，例如有界队列的 notEmpty 与 notFull。

**易错点：**

- 背诵锁升级阶段，却说不清业务为何需要互斥。
- 使用 ReentrantLock 后漏写 finally 解锁，异常路径永久占锁。

## Q35：ThreadPoolExecutor 的参数如何映射到真实负载？

**短回答：**

结论：线程池参数必须从任务等待时间、执行时间、下游容量和内存预算反推；无界队列或盲目增大 maximumPoolSize 都可能把过载藏成延迟与 OOM。

**原理：**

提交任务时，运行线程少于 corePoolSize 先建核心线程；否则尝试入队；队列满且未达 maximumPoolSize 才扩线程，最后触发拒绝策略。keepAliveTime 管理非核心线程空闲回收，也可选择作用于核心线程。CPU 密集任务线程数接近可用核数，I/O 等待任务可更高，但必须受连接池、数据库和远端限额约束。队列容量决定允许积压的时间窗口，应结合 Little 定律和超时目标评估。

## Q36：线上死锁怎样从现象定位到具体锁顺序？

**短回答：**

结论：先保留现场并确认线程确实在循环等待，再用 JVM 线程信息定位持锁者和等待者，最后回到统一锁顺序、缩小临界区或超时退让修复。

**原理：**

死锁需要互斥、持有并等待、不可剥夺和循环等待同时成立。线上表现可能是吞吐突然归零、线程池 active 满但 CPU 不高，也可能与连接池耗尽混淆。ThreadMXBean 或 jcmd Thread.print 可给出线程栈、监视器和 ownable synchronizer 信息；将“线程 A 持有 L1 等 L2、线程 B 持有 L2 等 L1”画成等待图即可确认。修复后还要检查数据库锁和外部资源，它们未必出现在 JVM 死锁检测中。

**代码 / 场景：**

订单迁移同时锁旧账户和新账户时，统一按账户 ID 从小到大获取；无法统一时使用限时 tryLock，失败释放已持有锁并带抖动重试。故障测试让两线程从相反方向同时进入，确认不会永久阻塞。

**递进追问：**

1. **ThreadMXBean 没报告死锁就能排除吗？**

   不能，数据库行锁、分布式锁和条件等待可能不在 JVM 可识别的监视器循环中。

2. **扩大线程池能解决死锁吗？**

   不能，只会增加更多等待线程和资源占用；必须破坏循环等待或调整临界区协议。

**易错点：**

- 把所有线程阻塞都叫死锁，没有画出资源等待环。
- 直接重启消除现场，却不保存线程转储和请求关联信息。

## Q37：Kafka 如何用 ACK、副本与 ISR 控制消息丢失窗口？

**短回答：**

结论：生产端 ACK 决定等待到哪一步，副本与 ISR 决定可容忍故障范围；要降低已确认消息丢失，需组合 `acks=all`、足够副本和最小同步副本，而非只改一个参数。

**原理：**

分区 Leader 接收写入并追加日志，Follower 拉取并追赶；ISR 表示当前保持足够同步的副本集合。`acks=0/1/all` 分别表示不等响应、只等 Leader、等待满足同步条件。若允许 ISR 只剩 Leader 仍接受写，Leader 随即故障时可能没有合格副本保留数据；设置 min.insync.replicas 可在同步副本不足时拒绝写，牺牲部分可用性换持久性。磁盘刷盘、机架故障域和不洁净选主也必须进入模型。

**代码 / 场景：**

支付事件分区配置 3 副本、跨机架分布，生产者使用 acks=all，并把最小同步副本设为 2。演练隔离一个再隔离两个 Broker，确认单故障仍写入、同步副本不足时明确失败，且已确认消息在新 Leader 上可读。

**递进追问：**

1. **acks=all 是否等于所有配置副本都写入？**

   不是，它等待当前 ISR 中满足配置条件的副本，ISR 规模与 min.insync.replicas 共同决定强度。

2. **副本越多是否只有好处？**

   副本会增加存储、网络复制和恢复成本，仍需按故障域与吞吐预算选择。

**易错点：**

- 只背 acks=all，不说明 ISR 缩小时是否继续接受写。
- 多个副本放在同一故障域，却按副本数宣称高可用。

## Q38：Kafka 重试后怎样避免消息与业务结果重复？

**短回答：**

结论：传输重试可由幂等生产者减少日志重复，消费端仍要把业务写入与消费进度设计为可重放；所谓 Exactly-Once 不能自动覆盖任意外部数据库。

**原理：**

客户端超时不知道 Broker 是否已写入，重试可能重复发送；幂等生产者用生产者 ID、分区与序列号去重同会话内重试。消费者拉取、处理、提交 offset 是三个动作，处理成功但提交前崩溃会再次收到同一消息。若结果写回 Kafka，可用事务协调输入 offset 与输出记录；若写 MySQL，则需唯一业务键、幂等表或本地事务同时记录处理状态。先提交 offset 再处理又会造成消息丢失。

**代码 / 场景：**

优惠券发放以 `event_id` 建唯一索引，在同一数据库事务内插入处理记录并发券；重复消费命中唯一约束后读取既有结果并正常推进 offset。故障测试在业务提交后、offset 提交前杀消费者，验证只发一张券。

**递进追问：**

1. **手动提交 offset 就能杜绝重复吗？**

   不能，只能选择提交时机；业务成功到 offset 成功之间仍存在崩溃窗口。

2. **Kafka 事务能原子写 MySQL 吗？**

   不能直接覆盖任意外部数据库，仍需 outbox、幂等键或专门一致性协议。

**易错点：**

- 把至少一次投递错误描述成消费者只会收到一次。
- 先提交 offset 再执行外部副作用，失败后消息无法自动重放。

## Q39：RocketMQ 顺序消息与事务消息分别解决什么问题？

**短回答：**

结论：顺序消息约束同一消息组内的存储和消费次序，事务消息协调本地事务与消息最终可见；二者解决的问题不同，也都不能替代消费幂等。

**原理：**

要保持订单事件顺序，应以订单 ID 作为消息组/队列路由键，让同一订单进入同一有序通道，并让消费者按协议串行处理；全局顺序会牺牲并行度。事务消息先发送半消息，再执行本地事务并提交或回滚消息；Broker 在状态不明时回查生产者。生产者本地事务状态查询必须可靠，消费者仍可能因重试看到重复事件。死信是多次消费失败后的隔离结果，需要告警和人工/自动修复流程。

**代码 / 场景：**

订单创建、支付、关闭事件按 orderId 分组，消费者维护状态机拒绝非法逆序；创建订单与发布事件使用事务消息，回查根据本地事务记录返回明确状态。注入网络超时和重复投递，验证状态机与幂等键。

**递进追问：**

1. **为什么不追求所有订单全局有序？**

   全局单队列会限制吞吐，业务通常只要求同一聚合根内有序，不同订单可以并行。

2. **事务回查返回未知怎么办？**

   应保留可查询的本地事务记录，持续回查或进入人工处置，不能随意提交半消息。

**易错点：**

- 把顺序消息误说成整个 Topic 所有消息绝对有序。
- 使用事务消息后取消消费者幂等与状态校验。

## Q40：秒杀中 Redis 扣减与数据库落库怎样避免超卖和丢单？

**短回答：**

结论：Redis 可承担入口原子预扣与削峰，但库存事实、订单幂等和失败补偿必须落到可审计存储；不能把异步落库描述成天然最终一致。

**原理：**

请求先校验活动与幂等键，再用 Lua 在 Redis 原子检查库存并扣减，同时生成待处理事件；消费者以业务唯一键创建订单，并用数据库条件更新或唯一约束兜底。消息发送失败可通过 outbox、可靠队列或待处理集合重放；数据库失败要明确重试、补偿返还或人工对账。Redis 主从切换可能丢失刚确认的预扣，因此容量超售容忍度决定是否仍需数据库强约束。

**代码 / 场景：**

用户每场活动只抢一次，以 `(activity_id,user_id)` 建唯一索引。压测同时提交重复请求、杀消费者、切 Redis 主节点，再核对 Redis 余量、成功订单、待补偿事件三者守恒，而不是只看接口返回成功数。

**递进追问：**

1. **什么时候写数据库最合适？**

   入口同步写可获得更强确认但吞吐受限；异步写需可靠事件、幂等和补偿，必须按 SLO 取舍。

2. **Lua 扣减成功就一定不会超卖吗？**

   只能保证该 Redis 实例上的原子预扣，故障切换、重复消费和数据库写入仍需独立约束。

**易错点：**

- 只设计扣减，不设计消息丢失、落库失败和库存返还。
- 把接口成功数当成订单事实，不做跨存储对账。

## Q41：万台机器文件分发的控制面怎样扛住状态洪峰？

**短回答：**

结论：文件数据面应就近并行下载并校验内容，控制面负责版本、调度和汇总；节点状态要批量、幂等、可重放，不能让每个心跳同步写主库。

**原理：**

原文件先生成内容哈希和不可变版本，分发可借助对象存储/CDN、分层中继或节点互传降低源站带宽。控制面把任务切分，节点以 `(task,node,attempt,seq)` 上报状态，经 Kafka 等缓冲后批量聚合；乱序与重复用序列号和状态机处理。Kafka 故障时节点保留本地 WAL、指数退避，恢复后重放。任务完成条件必须同时满足目标节点集合、正确哈希和超时/豁免策略。控制面元数据跨机房复制并有明确主写切换协议。

**代码 / 场景：**

发布 10GB 模型到一万节点时，节点下载后校验 SHA-256，仅上报阶段变化和周期摘要。压测模拟一万节点同时完成、Kafka 中断半小时、A 机房切 B 机房，核对最终完成数、重复事件和错误文件隔离。

**递进追问：**

1. **为什么不能只统计“收到完成消息”的数量？**

   消息可能重复、伪成功或对应旧 attempt，必须校验节点身份、版本、序列和文件哈希。

2. **Kafka 恢复后如何避免旧状态覆盖新状态？**

   聚合端按 attempt 与单调序列比较，只接受更新版本，旧事件保留审计但不回退状态。

**易错点：**

- 让所有节点直接高频更新同一任务行，制造数据库热点。
- 只保证传完，不验证内容哈希和目标节点集合是否完整。

## Q42：错误率驱动的自适应限流器如何避免阈值振荡？

**短回答：**

结论：限流需要线程安全地发放许可，并用平滑错误率和迟滞调整阈值；采样不足、下游超时和恢复探测必须进入状态机，不能见错就砍半、见好就放开。

**原理：**

许可路径可用原子计数、Semaphore 或令牌桶限制并发/速率；反馈路径在固定或滑动窗口统计请求数、错误数与延迟。只有样本达到下限才调整，连续恶化时乘性降低，稳定恢复时加性增加，并设置上下界、冷却时间和迟滞区间。被本地拒绝的请求不能计为下游错误，否则会形成自激反馈。半开阶段只放少量探测请求，配置变更要原子发布。

**代码 / 场景：**

支付依赖正常并发上限 200，窗口内至少 100 次请求才评估；错误率持续两窗超过 5% 时降为 70%，稳定五窗后每次增加 10。并发压测注入 30% 超时后恢复，验证阈值单调收敛、无大幅摆动。

**递进追问：**

1. **为什么要设最小样本数？**

   少量请求中一次失败会产生极端比例，直接调节会让低流量时阈值剧烈波动。

2. **限流与熔断有何区别？**

   限流控制进入系统的速率或并发，熔断依据失败状态暂时阻止调用并安排恢复探测。

**易错点：**

- 把本地拒绝也统计为下游失败，形成错误率正反馈。
- 没有冷却和迟滞，阈值在边界附近频繁升降。

## Q43：TCP 第三次握手丢失后双方状态如何收敛？

**短回答：**

结论：客户端发送最终 ACK 后可进入 ESTABLISHED，服务端仍停留在 SYN-RECEIVED 并重传 SYN-ACK；客户端收到重传后再次 ACK，最终建立或由服务端超时放弃。

**原理：**

第一次 SYN 携带客户端初始序列号，服务端回复 SYN-ACK 确认并给出自己的序列号，第三次 ACK 确认服务端序列空间。ACK 本身通常不单独重传，但服务端未收到会重传 SYN-ACK，这会触发客户端再次确认。若客户端随后发送数据，其 ACK 信息也可能让服务端完成确认；若持续不可达，重试耗尽后半连接被清理。三次握手同时验证双向通信并同步序列号，不只是“连接三次”。

**代码 / 场景：**

用网络故障注入丢弃客户端第三个包，抓包观察 SYN-ACK 重传、客户端重复 ACK 和连接状态；同时监控 SYN backlog，验证攻击或丢包情况下半连接不会无限占用。

**递进追问：**

1. **第二次握手后双方分别是什么状态？**

   服务端通常为 SYN-RECEIVED，客户端收到有效 SYN-ACK 后发送 ACK 并进入 ESTABLISHED。

2. **为什么两次握手不足？**

   服务端无法确认客户端已收到自己的序列号和应答，旧延迟 SYN 也更难被可靠区分。

**易错点：**

- 机械背状态名，却说不清丢包后的重传触发者。
- 把 TCP 可靠性等同于应用业务只执行一次。

## Q44：HTTP 长连接与 WebSocket 在服务端架构上怎样选择？

**短回答：**

结论：HTTP keep-alive 复用传输连接但仍按请求响应交互，WebSocket 握手后提供双向消息通道；是否需要服务端主动推送、连接规模和中间设施支持决定选型。

**原理：**

HTTP 持久连接减少重复建连成本，HTTP/2 还能在单连接多路复用请求，但应用语义仍是客户端发起。WebSocket 通过 HTTP Upgrade 建立后使用独立帧协议，双方均可主动发送；服务端需管理长连接、心跳、背压、重连、会话路由和滚动发布。代理空闲超时、连接迁移和消息顺序都需显式处理。若只是单向事件流，也可评估 SSE，避免引入双向协议复杂度。

**代码 / 场景：**

IM 在线消息使用 WebSocket，网关按用户路由连接，离线消息仍落持久存储；普通订单查询继续用 HTTP。演练网关重启和代理空闲超时，确认客户端带游标重连后能补齐消息且不会重复展示。

**递进追问：**

1. **keep-alive 是否代表服务端可随时推送业务消息？**

   不代表，它主要复用底层连接，普通 HTTP 语义仍由请求触发响应。

2. **WebSocket 连接断开后如何保证消息不丢？**

   协议本身不保存业务历史，需要服务端持久化序号、客户端确认与断线补拉机制。

**易错点：**

- 把 TCP 长连接、HTTP keep-alive 和 WebSocket 当成同一概念。
- 只实现心跳，不设计消息持久化、背压和断线补偿。

## Q45：从输入 URL 到 CDN 回源应怎样画完整链路？

**短回答：**

结论：先解析 URI 与缓存策略，再经 DNS 获得边缘地址，建立 TCP/TLS 并发送 HTTP；CDN 命中直接响应，未命中才按回源规则访问源站并缓存合格内容。

**原理：**

浏览器先检查 URL、HSTS 和本地缓存，再通过系统/递归解析器查询 DNS；权威 DNS 或调度系统返回适合的边缘节点。客户端建连并完成 TLS，HTTP 请求携带 Host 等信息。CDN 根据 cache key、过期与校验头判断命中，miss 时向源站或上级缓存请求。动态鉴权内容若错误共享 cache key 会泄露数据，Cookie、Authorization、Vary 与查询参数都影响缓存边界。DNS TTL 与 CDN TTL 是两个不同层次。

**代码 / 场景：**

公开题库静态资源使用带内容哈希 URL 和长缓存，HTML 使用短缓存或协商验证；登录用户 API 明确不进入公共缓存。用 dig、curl 响应头和 CDN 日志验证解析、Age、Cache-Status 与回源率。

**递进追问：**

1. **DNS 命中缓存后是否不再访问 CDN？**

   不是，DNS 缓存只省去名字解析，HTTP 请求仍会发送到解析得到的 CDN 节点。

2. **CDN 为什么可能缓存错用户内容？**

   cache key 未包含必要鉴权维度或忽略响应缓存指令时，不同用户可能共享同一对象。

**易错点：**

- 把 DNS 缓存和 HTTP/CDN 内容缓存混为一层。
- 动态私有响应未设置缓存边界，造成跨用户数据泄漏。

## Q46：进程、线程与上下文切换怎样对应 Java 服务开销？

**短回答：**

结论：进程提供独立地址空间与资源边界，线程共享进程资源但拥有执行上下文；切换需保存调度状态并可能破坏缓存局部性，线程越多不等于吞吐越高。

**原理：**

同一进程线程通常共享代码、堆和打开文件，每个线程有寄存器、栈、调度状态与线程局部数据。调度器切走任务时保存必要 CPU 上下文，恢复另一个任务；跨进程还可能切换地址空间映射并影响 TLB。阻塞 I/O、锁竞争和过多可运行线程都会增加调度与缓存抖动。Java 线程与操作系统线程的具体映射由实现决定，现代常规 HotSpot 平台通常采用一对一；虚拟线程则把大量 Java 任务调度到较少载体线程。

**代码 / 场景：**

把接口线程池从 200 扩到 2000 后若吞吐不升、上下文切换和 p99 激增，应回查下游瓶颈和阻塞点。用负载测试同时记录 runnable 线程、锁等待、cswch、CPU 与连接池，而非只看线程数。

**递进追问：**

1. **线程切换一定比进程切换便宜吗？**

   通常地址空间共享减少部分成本，但具体仍取决于缓存、内核路径和工作集，不能当绝对常数。

2. **虚拟线程能消除下游容量限制吗？**

   不能，它降低大量阻塞任务的线程管理成本，数据库连接和远端吞吐仍需限流。

**易错点：**

- 把线程共享资源误说成共享调用栈和寄存器。
- 用无限线程掩盖慢下游，最终增加调度与内存压力。

## Q47：后端鉴权如何同时防越权、重放与 XSS 影响？

**短回答：**

结论：认证只确认主体，授权必须在服务端逐资源校验；敏感操作还需短期凭据、重放防护和输出编码，不能依赖前端隐藏按钮或只验 JWT 签名。

**原理：**

登录建立主体后，每个请求验证令牌签名、issuer、audience、有效期和撤销策略，再按主体与资源关系做对象级授权。高风险写操作可加入 nonce、时间窗、幂等键和二次确认。XSS 通过不可信内容在浏览器执行，服务端应按输出上下文编码并设置安全响应策略；HttpOnly 可降低脚本直接读取 Cookie 的风险，却不能阻止脚本以用户身份发请求。日志不得记录完整令牌与敏感字段。

**代码 / 场景：**

用户访问 `/orders/123` 时，后端必须查询订单归属或权限关系，不能因 URL 可猜就返回。支付回调校验签名、时间戳和唯一事件 ID。安全测试用另一个普通账号枚举 ID、重放相同请求并注入脚本，确认均被正确处理。

**递进追问：**

1. **JWT 验签成功为什么仍可能越权？**

   签名只证明令牌未被篡改及其声明来源，访问具体对象仍需服务端授权判断。

2. **HttpOnly 能完全防住 XSS 吗？**

   不能，脚本虽难读取 Cookie，仍可能发起带 Cookie 的操作或读取页面中的敏感数据。

**易错点：**

- 把按钮隐藏和路由守卫当作服务端授权。
- 只验签名，不校验过期、受众、签发者和重放边界。

## Q48：高并发短链服务如何处理碰撞、热点与过期？

**短回答：**

结论：短码必须可唯一解析并处理碰撞，读路径可缓存映射但事实仍在持久层；设计还要覆盖恶意枚举、热点短链、失效时间和重定向语义。

**原理：**

生成可用全局 ID 做 Base62 编码，或对原 URL 哈希后检测冲突并加盐；前者易保证唯一，后者利于相同 URL 去重但需要碰撞协议。映射表对 shortCode 建唯一索引，保存目标、租户、创建者、过期和状态。访问先做格式/风控校验，再读缓存和数据库，返回 301 或 302 取决于目标是否稳定及缓存期望。热点可多级缓存，过期和删除要防旧缓存复活。统计点击事件应异步，不能阻塞跳转。

**代码 / 场景：**

营销短链使用随机化 Base62 ID，数据库唯一约束兜底；缓存 TTL 不超过业务过期，禁用时发布失效事件并在回源再次核对状态。压测单热点百万 QPS、随机枚举和过期边界，确认源库与跳转延迟。

**递进追问：**

1. **301 与 302 如何选择？**

   永久稳定映射可考虑 301，但浏览器和中间缓存更难撤回；需可修改或统计控制时常用 302。

2. **只用 URL 哈希截断为什么有风险？**

   有限短码空间必然可能碰撞，必须检查唯一约束并定义重试、加盐或冲突链。

**易错点：**

- 假设哈希截断绝不碰撞，没有数据库唯一约束。
- 缓存时间超过业务过期时间，禁用后仍继续跳转。
